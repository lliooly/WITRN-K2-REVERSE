# 研究主线与证据阅读方法

本目录按方法恢复、固件、图片、E-Mark 和遥测组织分析记录。每个主题列出输入版本、分析结论、来源函数、复核方法和验证范围。

## 先认识三个分析对象

| 对象 | 程序类型 | 研究问题 | 主线 |
| --- | --- | --- | --- |
| WITRN UP V30 / `WITRNUP.dll` | 受保护的 .NET 主程序集 | 恢复方法体、识别 HID / DFU、固件升级、虚拟 E-Mark | [方法恢复](01-method-recovery.md)、[固件 / DFU](02-firmware-dfu.md)、[E-Mark](04-emark.md) |
| K2Picture 1.1 / `K2Picture.dll` | 受保护的 .NET 图片工具 | `.pic` 参数、RGB565、图片区域与资源 worker | [表盘与图片](03-picture.md) |
| WITRN PC V1.0.4 / `WITRN.exe` | 原生 x86_64 Qt 上位机 | 被动遥测、CSV / SQLite 和时间字段 | [遥测与交换格式](05-monitor-files.md) |

输入的精确 SHA-256 见 [复现指南](../docs/reproduction.md)。上述程序不是同一个程序集；RID 只在对应程序集内有意义，不能把 K2Picture 的 RID 和 UP V30 的 RID 混用。

## 阅读顺序

1. [方法恢复](01-method-recovery.md)：解释为什么初始反编译的短方法体不能直接代表真实逻辑。
2. [固件与 DFU](02-firmware-dfu.md)：把格式、帧、调用顺序和 Flash 布局串成一个升级事务。
3. [表盘与图片](03-picture.md)：区分配置文件、像素结构、有效长度与擦除分配范围。
4. [虚拟 E-Mark](04-emark.md)：区分单条文件、10 组集合、电脑工程及两个独立扇区。
5. [遥测与文件交换](05-monitor-files.md)：区分普通模式读数、电脑记录和官方交换格式。
6. [关键函数索引](functions/README.md)：从结论回到程序集 RID、代理 token 或原生函数地址。
7. [验证矩阵](../docs/validation.md)：判断哪些可以由合成测试复核，哪些有单台实机依据。

## 证据类型

| 标签 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 静态证据 | 特定输入中的结构、常量、调用和主机流程 | 所有设备实际都这样响应 |
| 合成测试 | 独立实现的布局、保留字节、流程和错误处理 | 官方文件与真实 USB 时序兼容 |
| 实机读取 | 特定设备 / 版本的报告、校验和只读性能 | 擦写与恢复一定成功 |
| 实机擦写 | 特定设备的一次写入及读回 / 设备持有者确认 | 其他版本和所有资源恢复兼容 |
| 推算 | 基于现有测量估算其他流程耗时 | 已经实际执行该完整流程 |

每个主题使用相同的“结论 → 来源函数 → 数据布局 → 操作流程 → 验证边界”结构。正文中的中文函数名称是研究者赋予的职责标签，不是厂商公开 API 名称。

## 原文件放在哪

`reverse/` 保留静态工具和较详细的专题报告，`docs/` 保留完整协议及实测记录，`k2up/` 是独立参考实现，`tests/` 是合成 / 模拟检查。各专题通过链接连接详细报告、参考实现和测试。

原应用的 UI 布局和打包资料移入 [应用背景附录](../archive/application/README.md)。它们不参与协议证据链。
